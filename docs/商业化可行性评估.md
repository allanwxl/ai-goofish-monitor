# 闲鱼监控 MCP 数据服务商业化可行性评估

> 版本：v1.0　｜　评估日期：2026-11-10
> 评估对象：`ai-goofish-monitor` 项目对外提供 MCP 数据服务的可行性、路径与风险边界
> 定位：**收费仅用于覆盖模型调用、服务器损耗与电费，不以盈利为目的**

---

## 1. 结论摘要

**结论：有条件可行。**

技术侧几乎没有阻力 —— 现有的查询服务函数可以直接映射为 MCP 工具，MCP 层本质是薄封装。真正的约束不在代码，而在**合规边界、单位经济与数据覆盖广度**三处。

### 1.1 三个关键判断

**判断一：成本结构对数据产品是友好的。**

MCP 查询侧的边际成本约等于零（本地 SQLite 读取），全部变动成本集中在爬取与 AI 分析，且这部分成本**只随覆盖关键词数增长，不随客户数增长**。这是"数据产品"而非"算力转售"的正确结构 —— 客户越多，每人的固定成本分摊越低。

**判断二：成本转嫁模式下单位经济天然自洽。**

只要定价公式中包含固定成本分摊，收入与成本恒等，无需任何利润缓冲：

```
定价:      月费(K) = K × $3.94 + F_c / P
付费成本:  P × K × $3.94
总收入:    P × 月费(K) = P × K × $3.94 + F_c
总成本:    P × K × $3.94 + F_c
⟹ 收入 − 成本 = 0
```

**前提条件（不可违反）**：免费档不得允许建任务。否则免费用户会触发 AI 成本，打平公式立即失效。

**判断三：合规是本方案的真正瓶颈，但存在明确的差异化抗辩。**

北京互联网法院 2026 年 6 月首例数据专款案（爬取平台数据→搭建网站→对外售卖访问权）判赔 23 万余元，是必须规避的红线样本。本方案在三个维度上与其有本质差异：使用正常登录态（未绕过访问控制）、输出加工后的市场情报（非原样转售）、且收费仅覆盖成本（非"以销售数据为主营业务"）。

### 1.2 单位经济关键数字

| 指标 | 数值 | 来源 |
|---|---|---|
| 单商品 AI 分析成本 | ≈ $0.0073 | 实测 token × 官方定价推导 |
| 关键词合规审核成本 | ≈ $0.0001 / 次 | 推导 |
| 建任务单次成本（一次性跑） | ≈ $0.131 / 次 | 推导 |
| **覆盖 1 个关键词的月成本** | **≈ $3.94** | 推导 |
| 覆盖 200 关键词的月 AI 成本 | ≈ $788 | 推导 |
| 盈亏平衡付费用户数（$19/月、80% 毛利） | 52 – 66 人 | 推导 |
| 成本转嫁模式下的基础档月费 | ≈ $4.6 / 月（≈ ¥33） | 推导 |

> **关键结论：每 4 个付费用户即可养 1 个关键词的监控覆盖。**

### 1.3 前置条件

本方案成立需要同时满足：

1. **数据覆盖广度** —— 当前仅覆盖 1 个关键词、14 条商品、150 条价格快照，远不足以构成可售服务。数据是瓶颈，不是代码。
2. **关键词合规审核** —— 一旦允许第三方下发抓取指令，平台即从"自用工具"变为"受托执行方"，审核机制是控制该风险的主闸门。
3. **显式接受合规敞口** —— 风险不随工程投入下降，只会随规模放大。
4. **成本监控与止损开关** —— 成本转嫁模式无利润缓冲，必须能自动暂停新建任务。

## 4. 关键词合规审核机制

### 4.1 定位

建任务的**前置闸门**。既是风控，也是抗辩证据链 —— 平台在代客户执行抓取前完成关键词合法性审查并留痕，既过滤违禁品类与垃圾关键词，又证明平台履行了审查义务。

### 4.2 审核维度

| 类别 | 判定要点 | 示例 |
|---|---|---|
| 违禁/受限品类 | 是否指向平台禁止或限制交易的品类 | 账号、证件、发票代开、处方药、烟草、野生动物、破解软件、外挂 |
| 个人可识别信息 | 是否指向特定自然人的隐私信息 | 真实姓名 + 电话、"XX 的身份证"、学生证、病历 |
| 平台限制品类 | 是否属于已下架或限制发布的品类 | 医疗器械、隐形眼镜、处方药、烟草 |
| 引流垃圾词 | 是否为批量套利/引流词，会拉回大量垃圾数据 | "9.9 包邮 全国"、"免费送"、"收手机"+"加V" |
| 关键词结构合法性 | 是否含 URL、联系方式、违禁字符 | 完整 URL、电话、微信、邮箱 |

### 4.3 实现要点

- **模型**：复用现有 MiniMax-M3.1-Flash（`AI_MAX_OUTPUT_TOKENS=32768`）。审核是短 prompt + 结构化 JSON 输出，**单次成本 ≈ $0.0001**，相对建任务的 $0.131 可忽略
- **输出结构**：`{verdict: "approved"|"rejected"|"needs_manual_review", reasons: [...], matched_rules: [...]}`
- **拒答处置**：`rejected` → 直接拒绝建任务并返回原因，**不消耗建任务配额**；`needs_manual_review` → 任务挂起为 `pending_review`，人工放行后才计入配额并进入调度
- **留痕**：审核记录（关键词、判定、理由、规则命中、时间、发起方 API Key）写入 `keyword_reviews` 表 —— 这是合规抗辩链的核心证据
- **独立暴露**：提供 `review_keyword` 工具供客户自查，避免"建了被拒"的挫败感

### 4.4 价值

审核留痕使平台在"代客户抓取"模式下，区别于"放任抓取"的服务商。在抗辩维度上，这是可举证的主观努力。

## 5. 成本模型

### 5.1 实测基线

| 项 | 实测值 | 来源 |
|---|---|---|
| 单商品分析耗时 | 45 分 18 秒 / 18 商品 = **2.51 分钟/商品** | `logs/ai/` 18 条记录，`20261106_141206` → `20261106_145724`（任务「小米17promax」），含详情页 + 图片下载 + 6–9 图多模态分析 |
| 单次调用 token | `prompt_tokens` 14751、`reasoning_tokens` 6527、`content` ≈ 3009 字符 | 6 图 + 真实 prompt 实测 |

### 5.2 模型单价

MiniMax-M3.1-Flash：**输入 $0.15 / 1M tokens、输出 $0.60 / 1M、缓存读取 $0.015 / 1M**
（人民币：输入 1 元、输出 4 元、缓存 0.1 元 / 百万 token）

来源：[MiniMax API 定价页](https://platform.minimax.io/docs/pricing/overview) ｜ [M3.1 Flash 发布公告](https://www.minimax.io/blog/minimax-m31f)

### 5.3 单商品成本推导

```
输入: 14751 tokens × $0.15 / 1e6 = $0.0022
输出: (6527 reasoning + ≈2000 content) × $0.60 / 1e6 = $0.0051
────────────────────────────────────────────────────────────
单商品 AI 成本 ≈ $0.0073   （9 图场景输入 token 更高，估 ≈ $0.0085）
```

> 精确值为 $0.00732885。**全文统一采用 $0.0073 的近似口径**，以保证后续各表的数字互相自洽（见 §12.3 的复算脚本）。

### 5.4 三类动作的成本归因

| 动作 | 成本性质 | 成本量 | 计算 |
|---|---|---|---|
| 合规审核 | 昂贵但极小 | ≈ $0.0001 / 次 | 约 200 输入 + 100 输出 token |
| **建任务（一次性跑）** | **昂贵** | ≈ $0.131 / 次 | 18 商品 × $0.0073 + 审核 |
| **建任务（持续监控）** | **昂贵且持续** | ≈ $3.94 / 月 / 关键词 | 18 × 30 天 × $0.0073 |
| **拉取任务结果** | **廉价** | ≈ $0 | SQLite 读，仅消耗带宽与 CPU |
| 查看所有结果列表 | 廉价 | ≈ $0 | 同上 |

### 5.5 固定成本

用户未指定服务器口径，按三档情景参数化（**待填入实际值**）：

| 情景 | 构成 | 月成本估算 |
|---|---|---|
| 低（自有 NAS） | 电费（80W × 720h ≈ 58 kWh × ¥0.6）+ 存储 ¥10 + 域名 ¥1 | ≈ ¥46 / 月（$6.4） |
| 中（自有机器 + 对象存储） | 电费 + 存储 ¥50 + 带宽 ¥30 + 域名 | ≈ ¥120 / 月（$16.7） |
| 高（付费云主机） | 月租 + 存储 + 带宽 | ≈ ¥300 / 月（$41.7） |

### 5.6 覆盖能力

- 串行：1440 分钟/天 ÷ 45 分钟/次 = **32 关键词/天**
- 并发 8（每 Chromium 实例约 300MB，8GB 内存）：约 **256 关键词/天**
- 覆盖 200 关键词：月 AI 成本 ≈ **$788**；覆盖 256 关键词：≈ **$1,009**

### 5.7 打平公式

设：付费用户数 P、免费用户数 F、固定成本 F_c、付费档含 K 个持续监控任务：

```
定价:      月费(K) = K × $3.94 + F_c / P
付费用户成本: P × K × $3.94
总收入:     P × 月费(K) = P × K × $3.94 + F_c
总成本:     P × K × $3.94 + F_c
⟹ 收入 − 成本 = 0
```

**由此得出的硬约束：**

1. **免费档不得允许建任务** —— 否则免费用户触发 AI 成本，打平公式失效
2. 免费用户仅可 `list_all_results` + 有限次 `fetch_task_results`（≈$0 成本）
3. 付费用户数越多，每人分摊的固定成本越低 → 定价可随规模下调

### 5.8 示例定价

以 F_c = $6.4、P = 10 为例：

| 档位 | 持续监控任务数 K | 月费 | 折合人民币 |
|---|---|---|---|
| 免费 | 0（不可建任务） | $0 | ¥0 |
| 基础 | 1 | $4.58 | ≈ ¥33 |
| 标准 | 3 | $12.46 | ≈ ¥90 |
| 团队 | 10 | $40.04 | ≈ ¥288 |

> 随 P 增大，各档月费均应下调（分摊项 $F_c/P 递减），建议按季度复核。

## 6. 计费模型

### 6.1 三个计费动作

| 动作 | 计费方式 | 额度设计 | 覆盖的成本 |
|---|---|---|---|
| `create_task` | **月度次数配额** | 基础档 3 次/月、标准档 10 次/月；超出按次加购 | 建任务 AI 成本 $0.131 + 持续监控 $3.94/月 + 固定成本分摊 |
| `fetch_task_results` | **按次计量** | 档位内含配额（如 500 次/月），超出按次计费 | 带宽与运维（≈$0，需覆盖支付通道成本） |
| `list_all_results` | 免费 | 无限制 | ≈ $0 |

### 6.2 "按次收费"的实现形态

MCP 单次查询的边际成本约等于零，逐次即时扣款的通道手续费（微信/支付宝 0.6%，Stripe 国际约 30%）与计量工程成本可能高于收入 —— 这是 MCP 商业化的公认难点（业内共识："meter 才是产品本身，支付只是细节"）。

因此推荐实现为：**按次计量 + 周期打包结算**

- 档位内含一定次数（如 500 次/月），不逐次扣费
- 超出部分按次计价，**周期汇总结算**（而非每次调用走支付）
- 计量必须**幂等**：以 `(request_id, tenant_id, tool_name)` 唯一约束去重，避免客户端重试造成重复计费

纯即时按次扣款作为备选，其代价是支付通道费用与计量工程复杂度显著上升。

### 6.3 月度配额实现要点

- 计数表 `task_quota_usage(tenant_id, period, used_count)`，用 `INSERT ... ON CONFLICT DO UPDATE` **原子递增**，避免并发超发
- **配额检查与占用必须在同一事务内完成**（check-and-consume），否则并发建任务会超配额
- 配额检查置于中间件层、**在任何昂贵逻辑之前**（避免超额后仍消耗爬虫资源）
- 配额耗尽返回 429 + 明确的重置时间（自然月）

## 7. 市场与定价

### 7.1 MCP 商业化惯例

- **MCP 不作为商品卖**，卖的是背后的数据订阅。Claude Code 市场约 318 个 MCP server，绝大多数 $0，收费的从 **$19/月**（独立开发者可持续线：基础设施 + 80% 毛利）到 $149/月（企业版）；$5–15/月档位基本空缺
- **数据类 MCP 的真实成交价在中高位**：Ahrefs Lite $129（带 MCP）、Peec AI $80、AIclicks Pro $189、Bright Data Scale $499/月起
- **按量计费的参照**：DataForSEO $0.0006/请求起（预付最低 $50）

来源：[Surferstack MCP 成本指南](https://surferstack.com/guides/mcp-server-costs-in-2026-what-you-pay-for-seo-and-ai-visibility-access-across-10-platforms) ｜ [UsageBox MCP 计费指南](https://usagebox.com/articles/how-to-charge-for-mcp-server-2026-per-call-subscription-x402) ｜ [Codango 定价实践](https://codango.com?p=268683/)

### 7.2 本方案的定位差异

成本转嫁模式下定价（基础档 ≈ $4.6/月）**远低于市场均价**。

- **好处**：进入门槛极低、易于获客；无需市场教育
- **代价**：规模效应才能覆盖固定成本，且**几乎无利润缓冲** —— 任何成本上升（模型涨价、服务器扩容、账号封禁导致爬取效率下降）都直接侵蚀本金

因此**必须配套成本监控告警**（单商品 AI 成本、单位关键词月成本、爬虫成功率），任一指标超阈值即自动暂停新建任务。

若 P4 之后数据质量与广度得到验证，存在向上调价空间（市场同类服务成交于 $80–$499/月），但那属于"做利润"的另一种定位，需重新评估合规抗辩。

### 8.2 本方案的差异化抗辩

1. **非原样转售** —— 输出 AI 多模态分析结果 + 价格历史快照 + 降价信号 + 市场参考价，是加工后的市场情报，非平台原始数据集合
2. **不构成实质性替代** —— 闲鱼核心业务是交易撮合与流量分发；市场数据分析报告不替代其任何功能，Agent 开发者亦非闲鱼用户

4. **不从事交易行为** —— 不代下单、不代发布、不养号刷量，与群控软件案关键区分
5. **收费仅覆盖成本，不以牟利为目的** —— 资金用途为模型调用、服务器损耗与电费，非"以销售数据为主营业务"。这在经营动机维度上是重要抗辩点（被诉案例中被告"以销售非法获取的数据内容为主营业务且销量较高"）
6. **平台履行审查义务** —— 建任务前经模型合规审核并留痕，平台对抓取内容实施必要管控

### 8.3 新形态带来的加重风险

允许第三方通过 MCP 下发抓取指令，使平台从"自用工具"变为**受托执行方**，这比纯只读数据服务的风险更高：

- 客户可能试图用平台抓取敏感或违规内容 → **关键词合规审核是控制此风险的主闸门**，其可靠性直接决定合规底线
- 客户行为导致的风控封号由平台承担 → 需要关键词审核 + 频率自律 + 账号池隔离 + 单租户熔断
- 商业化放大爬取规模 → 风控敞口随规模上升，**不会随工程投入下降**

### 8.4 必须自设的硬边界

- **只读数据面**：MCP 对数据只提供查询，绝不暴露写操作（不点赞、不关注、不评论、不下单、不改价）
- **建任务面受限**：只允许创建监控型只读任务，不允许任何自动化交互任务
- **不承诺时效**：不提供"实时/秒级"承诺
- **字段裁剪**：剥离卖家昵称、头像、个性签名、在售商品列表等个人信息；`raw_json` 不整体外发
- **频率自律**：单账号请求频率与覆盖量设上限，低于平台风控阈值
- **仅限商业情报用途**：服务条款禁止转售、训练竞品模型、骚扰等滥用
- **风险明示**：本项目**未获闲鱼官方授权**，这是已知且被接受的风险敞口

## 9. 架构方案

### 9.1 分层

```
Claude / Cursor / ChatGPT
        │  HTTP POST /mcp   (Streamable HTTP)
        │  Header: Authorization: Bearer <API_KEY>
        ▼
  src/mcp_server.py ──▶ src/mcp/server.py   (FastMCP 实例)
                            │  ① 鉴权 (StaticTokenVerifier)
                            │  ② 字段裁剪 (redact_record)
                            ▼
  src/mcp/tools.py ──▶ 现有服务层（零改动复用）
                            │  asyncio.to_thread → SQLite
                            ▼
                    data/app.sqlite3   (WAL：读不阻塞写)
```

爬虫进程（`spider_v2.py` 子进程）写库，MCP 进程读库，两条链路互不阻塞。

**MCP 服务必须独立进程部署**：Playwright Chromium 常驻内存会与 MCP 服务争抢资源，且崩溃隔离需要分开。

### 9.2 已实现（MVP，P2 阶段）

| 文件 | 职责 |
|---|---|
| `src/mcp/auth.py` | API Key 解析与校验（`secrets.compare_digest`），支持 `key` 与 `key:tenant` 两种形式 |
| `src/mcp/tools.py` | 4 个只读工具 + 统一出口裁剪 `redact_record()` |
| `src/mcp/server.py` | FastMCP 实例组装、鉴权挂载、`/health` 路由 |
| `src/mcp_server.py` | 独立启动入口 |
| `src/infrastructure/config/settings.py` | 新增 `MCPSettings`（`MCPSettings` + `reload_settings()` 同步） |

**工具集**：

| tool | 入参 | 返回 |
|---|---|---|
| `list_all_results` | 无 | 结果集清单：filename、keyword、商品数、最新爬取时间 |
| `search_items` | `keyword`、`page`、`limit`、`ai_recommended_only`、`keyword_recommended_only`、`include_hidden`、`sort_by`、`sort_order` | `{total_items, page, limit, items[]}` |
| `get_price_history` | `keyword`、`item_id`、`limit` | 价格快照序列 |
| `get_market_insights` | `keyword` | 均价/中位/区间、历史概览、日趋势 |

**分页语义**与既有 REST 接口 `/api/results/{filename}` 完全对齐（`page` ≥1、`limit` 1–100、`total_items`、两个推荐筛选互斥），使 Web UI 与 MCP 两条通道行为统一。

**字段裁剪策略**：采用**白名单**而非黑名单 —— 只允许外发明确列出的字段，新字段默认不出库，避免后续新增字段时遗漏脱敏。

| 保留 | 剥离 |
|---|---|
| 商品标题、售价、原价、想要人数、标签、发货地区、发布时间、商品ID、图片列表、主图、浏览量、商品链接 | 卖家昵称、卖家头像、卖家个性签名、卖家发布的商品列表 |
| 卖家信用等级、买家信用等级、在售/已售商品数、评价总数 | `ai_analysis.error`（内部实现细节） |

### 9.3 鉴权实现

使用 FastMCP 官方内置的 `StaticTokenVerifier`（`fastmcp.server.auth.providers.jwt`）：

```python
verifier = StaticTokenVerifier(tokens=token_map)
mcp = FastMCP(name="xianyu-monitor", auth=verifier)
```

实测行为（FastMCP 4.1.7 / MCP Python SDK 2.3.0）：

| 请求 | 响应 |
|---|---|
| 无 `Authorization` | 401 + `WWW-Authenticate: Bearer` |
| 错误 Key | 401 `{"error": "invalid_token", ...}` |
| 正确 Key | 200，正常列出工具并执行调用 |

**实现约束**：

- API Key 只从 `MCP_API_KEYS` 读取，不硬编码、不入库、不进仓库
- 校验在**每次工具调用**时执行（FastMCP auth 层保证），非仅连接建立时
- 比对用 `secrets.compare_digest`，且统一编码为 bytes 以支持非 ASCII Key
- 未配置 `MCP_API_KEYS` 时**拒绝启动**，而非放行全部
- 安全默认值：`MCP_ENABLED=false` + `MCP_HOST=127.0.0.1`

### 9.5 并发与状态语义

- 爬虫写、MCP 读是两条独立链路，SQLite **WAL 模式保证读不阻塞写** —— 架构成立的前提，**不可关闭 WAL**
- `busy_timeout=5000ms`：查询高峰遇 `SQLITE_BUSY` 需做有限次重试（建议 3 次、指数退避），再失败才报错
- **MCP 进程为只读角色**，不写业务表；启动时**不调用** `bootstrap_sqlite_storage()`（该函数只应由主应用启动时执行），避免多进程并发建表
- **配额 check-and-consume 必须原子**：利用 SQLite 单写者特性，用 `INSERT ... ON CONFLICT DO UPDATE` 原子递增实现；不能"先查后写"
- **全局爬虫并发上限**：进程内 `asyncio.Semaphore` 只在单 worker 内有效，多 worker 需共享计数（SQLite 租约表或 Redis）
- **公平调度**：单租户不得占满全局爬虫槽位，需每租户并发上限
- 令牌补充用 `time.monotonic()` 而非 `time.time()`（避免系统时钟回拨导致桶计算错误）

### 9.6 失败与恢复

| 情况 | 行为 |
|---|---|
| 审核失败/超时 | `create_task` 返回明确错误，不建任务、不计配额 |
| 配额耗尽 | 429 + 明确的重置时间 |
| 爬虫排队超限 | 返回"排队中"状态而非直接失败 |
| 建了任务但爬虫未启动 | 任务状态对客户可见，可重试 |
| 数据时效中断 | 查询结果暴露 `latest_crawl_time`，让 Agent 自行判断新鲜度，平台不静默返回陈旧数据 |
| 关键词无数据 | 返回空集 + 覆盖状态，而非报错 |
| 成本超阈值 | 自动暂停新建任务（成本转嫁模式无利润缓冲，必须有止损开关） |
| 库未初始化 | 返回可读错误（`ToolError`），不崩溃、不泄露堆栈与文件路径 |

### 12.3 成本测算可复算

全文统一采用**单商品 $0.0073** 的近似口径（精确值 $0.00732885），以保证正文各表数字互相自洽。

```python
# --- 单商品 AI 成本 ---
INPUT_TOKENS  = 14751   # 实测
REASONING      = 6527    # 实测
CONTENT        = 2000    # 3009 字符中文 ≈ 2000 token
PRICE_IN       = 0.15    # $/1M
PRICE_OUT      = 0.60    # $/1M

exact = INPUT_TOKENS/1e6*PRICE_IN + (REASONING+CONTENT)/1e6*PRICE_OUT
# 0.00732885  → 全文取 0.0073

per_item = 0.0073
ITEMS_PER_RUN = 18       # 实测：单关键词单次运行产出 18 条分析结果

# --- 单关键词月成本 ---
per_keyword_month = per_item * ITEMS_PER_RUN * 30
# 3.942  → 正文用 $3.94

# --- 覆盖成本与盈亏平衡 ---
monthly_ai_cost = per_keyword_month * 200          # 200 关键词 → $788
break_even = monthly_ai_cost / (19 * 0.8)          # $19/月订阅、80% 毛利
# 51.9 → 约 52 人（256 关键词时约 66 人）

# --- 打平定价 ---
def monthly_fee(k, fixed_cost, paid_users):
    return k * per_keyword_month + fixed_cost / paid_users

# 恒等式：P × monthly_fee(K, F_c, P) == P × K × per_keyword_month + F_c
# 例：F_c=6.4, P=10 → K=1: $4.58 | K=3: $12.46 | K=10: $40.04
```
